01 · Objective
What the model is built to do
Turn unstructured resumes into structured, searchable candidate knowledge
Every resume is parsed, normalized, and transformed to strict JSON before indexing
Rank candidates against a recruiter's natural-language query or a full job description
Semantic matching over skills, experience, projects, certifications — not keyword grep
Produce explainable results: bucket + score + strengths/weaknesses + reason
Every claim maps to a retrievable evidence chunk
Surface hidden gems — high-potential candidates rejected by years-based screening
Counteract years-of-experience bias with an explicit potential-scoring model

Two actors, one core

  • Applicant: upload → parse → index
  • Recruiter: query → retrieve → rank

    • Not "chat with your PDF"

  • Structured knowledge base first
  • LLM is a reasoner, never a free-form source

    • Trust by construction

  • Deterministic scores own the rank
  • LLM explains; it cannot invent scores

    An end-to-end retrieval-augmented ranking model
    Write path — indexing
    PDF upload → validation → digital text extraction
    OCR fallback for scanned documents (Tesseract / PaddleOCR)
    LLM structuring → strict JSON candidate profile (Pydantic-validated)
    Skill canonicalization + years-of-experience calculator
    Semantic chunking from the structured profile, not raw text
    Embeddings — BAAI bge-small-en-v1.5 (384-dim, CPU-friendly)
    Vector upsert into Qdrant (idempotent on chunk_id)
    Read path — ranking
    Query embedding (bge query-instruction prefix at search time only)
    Vector retrieval, grouped by candidate with section diversity
    Profile hydration from PostgreSQL (ground truth)
    Tier-1 deterministic scoring → overall score
    Tier-2 LLM reasoning over retrieved evidence only
    Bucket assignment: best / strong / hidden_gem / alternative
    Ranking persisted for audit; cached by query signature

    02 · Model description
    Ranking algorithm — two-tier, hybrid, evidence-based
    TIER 1 — Deterministic heuristic scoring
    skill_match — taxonomy overlap + semantic similarity
    experience_match — years ratio · domain cosine · progression
    education_match / certification_match — required criteria
    hidden_gem_score — potential signals, not years
    overall = weighted sum over active dimensions
      + bounded LLM delta (clamped ±0.08)
    Buckets via transparent rules, not LLM discretion
    best ≥ .80 & cov ≥ .7 · strong ≥ .60 & cov ≥ .5 · hidden_gem .45–.74 & HG ≥ .5 · alternative
    TIER 2 — LLM reasoning (evidence-constrained)
    Input: job intent + structured profile + bounded evidence pack (max N chunks)
    Output JSON: strengths · weaknesses · explanation · recommendation
    Must cite evidence_chunk_ids ⊆ retrieved — else reject & regenerate
    LLM delta clamped ±0.08 → cannot overturn a strong heuristic
    Fallback: LLM down → heuristic buckets remain, no narrative

    05 · Methodology
    How the model was designed and built
    Design-first, then build
  • 14-doc design package: architecture, ERD, API, AI/RAG/ranking pipelines
  • Clean Architecture + repository pattern + dependency injection (SOLID)
  • Ports & adapters — providers swapped via config, not code
    • Retrieval-augmented generation
  • Indexing: parse → structure → chunk → embed → upsert (idempotent)
  • Retrieval: embed query → Qdrant search → hydrate → rank
  • Optional hybrid BM25 + RRF fusion for low-recall queries
    • Two-tier ranking by design
  • Deterministic tier owns scores & buckets (transparent rules)
  • LLM tier explains & refines within a bounded delta
  • Deliberate decision: LLM explains "why", never decides the rank
    • Safety & guardrails
  • Schema-validated structuring with self-healing retry
  • Prompt-injection isolation; LLM never sees raw resume text
  • Post-validation: evidence chunk_ids must be subset of retrieved
    • Vertical slices, not big-bang
  • Each milestone runnable & demoable end-to-end (Phase 0 → 5)
  • Definition of done: tests green, lint clean, demoable UI
  • Eval-first: golden set + nDCG harness gate provider swaps

    06 · Challenges & learnings
    Problems encountered — and what we learned
    Challenges & how they were handled
    Messy / malformed resumes
    Strict JSON schema + validation, retry with error feedback, review queue
    LLM hallucination
    Evidence-only prompting; chunk_id subset post-validation; raw scores stay visible
    Prompt injection via resume text
    Delimiter-isolated prompts; injected strings land in text fields, never logic
    Provider lock-in & cost
    Ports + adapters; local BGE default; token budgets; caching
    Niche query recall
    Optional hybrid BM25 + reciprocal rank fusion
    Years-of-experience bias
    Explicit hidden-gem scoring model — potential signals, code-level & auditable
    Key learnings
    Deterministic rules should own the score; let the LLM explain, not decide
    Verifiability builds recruiter trust — every claim maps to a chunk
    Design-first (14 docs) avoided rework; vertical slices kept each milestone demoable
    Provider abstraction paid off: swap models/infra via config, zero business-logic changes
    Anti-bias is a product feature: hidden gems are surfaced with a clear reason

    08 · Demo
    How to see the model in action
    A public demo link is not yet deployed — the project is in early implementation. The model runs locally today:
    1 Start the stack docker compose up  (PostgreSQL + Qdrant + worker)
    2 Run the API uvicorn app.main:app  — health: GET /healthz
    3 Index resumes POST /api/v1/resumes  → pipeline: parse → structure → embed → upsert
    4 Rank candidates POST /api/v1/search/query  { "query": "senior Flutter engineer, payments" }
    5 Inspect evidence Response returns bucket, scores, explanation + evidence chunk_ids
