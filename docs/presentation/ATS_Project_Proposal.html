Executive Summary

We propose building an AI-Powered Applicant Tracking System (ATS) that converts raw resumes into structured candidate profiles, indexes them with semantic embeddings, and ranks applicants against recruiter queries or job descriptions using retrieval-augmented generation (RAG) plus LLM reasoning.

The system replaces today's keyword-matching shortlisting with semantic, explainable, bias-aware ranking. Recruiters get not only a ranked list — they get why each candidate matches, backed by citations to the resume. High-potential candidates with fewer years of experience are no longer discarded.

Why now

  • Manual screening consumes ~40% of recruiter time before first contact.
  • Keyword filters reject strong candidates who phrase experience differently.
  • LLM + vector-database tech is mature, cheap, and explainable enough for production.

What we deliver

  • A production-ready, deployable application in ~15 weeks (5 phases).
  • Resume ingestion, semantic search, explainable ranking, and a modern recruiter UI.
  • Provider-agnostic design — swap AI models and infrastructure without code changes.
Core promise: every candidate rank is a scored, explained, evidence-backed decision — replacing "gut feel and grep" with auditable AI.

The Problem

Recruiting teams struggle with three compounding issues that slow hiring and lower quality:

Pain pointImpact
Keyword matching Applicants are filtered by exact terms. A senior engineer who "built payments platforms" is invisible to a search for "banking experience". Strong candidates are lost before a human ever reads them.
No explainability Recruiters can't tell why one candidate ranked above another. Rankings are a black box, hard to defend, audit, or improve.
Years-of-experience bias Filters set minimum tenure, systematically excluding high-potential juniors and career-changers who bring fresh skills — even when they are the best fit.
Manual triage cost Reading and comparing resumes by hand consumes 30–40% of recruiter time per role, directly inflating cost-per-hire and time-to-fill.
The opportunity

A semantic, explainable system removes the trade-off: it searches meaning, not words; justifies every ranking; and actively surfaces hidden gems. The result is faster shortlists, higher quality, fairer screening, and a defensible audit trail for every hiring decision.

The Proposed Solution

An end-to-end platform with two actors and one shared knowledge core.

Core capabilities
CapabilityDescription
Smart resume ingestion Upload PDF → extract text (with OCR for scanned files) → LLM structures it into strict JSON → skills are normalized to a canonical taxonomy → content is chunked and embedded into a vector index.
Natural-language search Recruiters search the way they think: "senior Flutter engineer with banking payments experience". Semantic retrieval finds meaning, not exact keywords.
Explainable ranking A deterministic scoring engine (skills, experience, education, certification, hidden-gem signals) sets the rank; an LLM explains it with strengths, weaknesses, a recommendation, and citations to evidence chunks.
Hidden-gem detection An explicit potential model rewards skill depth, impactful projects, fast progression, leadership, and open-source work — so strong juniors are surfaced instead of filtered out.
Job-description matching Paste a job description and get the best candidates for that exact role, ranked and explained.
Transparency & audit Every ranking is persisted with scores, model versions, and evidence chunk IDs. All AI claims are traceable — a built-in hallucination guard.
How it works — high level

Applicant flow (index)

  1. Resume uploaded (PDF)
  2. Text extraction + OCR fallback
  3. LLM structures profile to JSON
  4. Skill canonicalization
  5. Semantic chunking + embedding
  6. Vectors stored (Qdrant), profile in PostgreSQL

Recruiter flow (rank)

  1. Natural-language query or job description
  2. Query embedded → vector search
  3. Candidate profiles hydrated
  4. Deterministic scores → bucket assignment
  5. LLM explanation (evidence-constrained)
  6. Ranked list: best / strong / hidden gem / alternative

Technology Stack

We select proven, swappable components. Every AI dependency sits behind a provider interface, so models and infrastructure can be changed via configuration — never code.

LayerChoiceWhy
FrontendFlutter (Material 3)One codebase for web, iOS, and Android; modern recruiter & applicant UIs.
BackendPython FastAPIAsync, typed, clean architecture; ideal for AI pipelines and REST APIs.
Relational DBPostgreSQLSource of truth for candidates, resumes, jobs, applications, and audit-logged rankings.
Vector DBQdrantHigh-performance semantic index; idempotent upserts and snapshotting.
EmbeddingsBAAI bge-small-en-v1.5384-dim, CPU-friendly, strong retrieval at low cost; swappable to larger models.
LLMProvider-agnosticOpenAI, Gemini, Ollama, vLLM, or any OpenAI-compatible endpoint — chosen by config.
OCRTesseract / PaddleOCRScanned-PDF fallback.
Async processingBackground workersResume pipelines and notifications off the request hot path.
Key design principles
  • Clean architecture — business logic is isolated and testable, independent of frameworks and AI providers.
  • Provider abstraction — embedding, LLM, vector store, and OCR are ports with adapters; swapping costs one config change.
  • Hallucination guard — the LLM ranks only from retrieved evidence; every claim carries a chunk ID.
  • Bias-aware by design — hidden-gem scoring is a transparent, auditable code-level model, not LLM discretion.

Project Scope

Included in the MVP (Phases 0–2, ~8 weeks)
  • Foundation: monorepo, CI, Docker Compose (Postgres + Qdrant), provider plumbing.
  • Resume ingestion: upload → extraction → LLM structuring → embeddings → vector index, with status tracking.
  • Search & deterministic ranking: natural-language search, intent parsing, skill/experience/education/certification scores, bucket assignment, hidden-gem detector.
  • Flutter screens: applicant upload, recruiter search, ranked candidate list, candidate detail.
  • Ranking persistence for audit and caching.
Included in the production release (Phases 3–4, ~7 more weeks)
  • LLM reasoning tier: strengths / weaknesses / recommendation / evidence with hallucination guard.
  • Job-description search and candidate comparison UI with evidence drill-down.
  • Auth & RBAC (JWT), rate limiting, upload validation and virus scan.
  • Observability: structured logs, tracing, metrics, error tracking.
  • Resilience: retries, circuit breakers, DLQ, GDPR erasure, re-index jobs.
  • Deployment: Terraform + CI/CD pipeline, staging environment.
Not in scope for v1 (post-launch backlog): interview-question generator, candidate fit scores, bias analytics, salary prediction, multilingual resumes, and AI resume improvement suggestions.

Risks & Mitigations

RiskImpact if unmitigatedMitigation
LLM structuring errors on messy resumes Broken profiles, silent data loss Strict JSON schema + validation, self-healing retries, manual-review queue, golden eval set.
RAG quality on niche queries Missed candidates Optional hybrid BM25 + reciprocal rank fusion; eval harness; embedding A/B tests.
Provider cost spikes Unpredictable budget Token budgets, caching, cheap structuring model, local BGE as default embedder.
Model / provider lock-in Inflexibility, inflated costs Ports + adapters; providers selected by config; swap gated by the same golden eval suite.
Regulatory compliance (GDPR) Fines, reputational harm Right-to-erasure API, audit logs, data-retention policy built in from Phase 1.
AI hallucination / wrong claims Poor hiring decisions Evidence-constrained prompts; chunk-ID subset validation; raw scores always visible.
Hidden-gem over-suggesting Noisy shortlists Tunable thresholds; explainable reasons; recruiter feedback loop.
Design-first insurance: the full design package (architecture, ERD, API spec, AI/RAG/ranking pipelines) is completed before build — cutting rework and giving the team a shared blueprint from day one.
